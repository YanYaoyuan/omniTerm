# omniTerm 路线图

omniTerm 面向 macOS、Linux 和 Windows，结合 iTerm2 式终端体验、MobaXterm 式远程连接工具与基于 Codex 的 Agent 模式。

当前仓库以 Codex 源码为基础，并提供首个 omniTerm 命令启动器。以下里程碑描述产品建设顺序，不代表这些功能已经全部发布，也不承诺尚未验证的交付日期。命令入口建立之后，优先建设三平台桌面终端和工作台内的 Agent 体验。

## 当前能力与目标

| 能力       | 当前基础                                                            | omniTerm 目标                                  |
| ---------- | ------------------------------------------------------------------- | ---------------------------------------------- |
| Agent      | `omniterm agent` 启动 Codex CLI/TUI；继承其工具执行、会话与审批实现 | 在工作台中显示任务、执行目标、审批、变更与结果 |
| 本地终端   | `omniterm shell` 启动系统 shell；仓库继承 PTY / ConPTY 组件         | 完整终端渲染、标签、分屏、搜索、配置           |
| SSH        | `omniterm ssh` 调用系统 OpenSSH                                     | 连接配置、密钥代理、跳板机、状态管理           |
| 端口转发   | `omniterm tunnel` 调用 OpenSSH 并传递转发参数                       | 本地 / 远程 / 动态转发管理、状态与清理         |
| SFTP       | `omniterm sftp` 调用系统 SFTP 客户端                                | 双栏文件浏览、队列、进度、取消和冲突处理       |
| 串口       | `omniterm serial` 调用可选的 pyserial miniterm                      | 设备发现、连接参数、收发、断连处理与日志       |
| 跨平台发行 | 上游已有平台相关源码与构建设施                                      | 独立验证和发布 omniTerm 三平台安装包           |

这些命令复用外部客户端，不等于已经有 omniTerm 图形界面、内建协议栈或统一会话管理。启动器要求 Node.js 22+，无 npm 运行时依赖；实际连接依赖本机对应客户端。安装方式和命令用法以根目录 [README](../../README.md) 为准。

## M0 · 开源项目基础

- 使用 omniTerm 名称、独立仓库和产品说明。
- 保留 Codex 来源、Apache-2.0 许可证与第三方声明。
- 明确新贡献的开发方式、功能状态和兼容性边界。
- 调整仓库维护入口与 CI，避免依赖上游组织的发布凭据。

**验收：** 新贡献者能从仓库首页理解现状、运行开发入口，并分辨可用功能与规划功能。

## M1 · 统一命令入口

- 提供 `omniterm` 命令，明确进入 Agent 或传统终端工作流。
- 首个 Agent 使用 Codex，支持明确指定引擎可执行文件。
- 提供本地 shell、SSH、SFTP、SSH 转发和串口的基础入口。
- 对缺失依赖、无效参数、连接失败和退出状态给出明确反馈。
- 保留底层客户端的主机密钥验证与认证交互。
- 提供 `doctor` 诊断依赖；串口支持明确标注可选的 pyserial 安装要求。

**验收：** 在三平台验证参数传递、含空格路径、Ctrl+C、退出码和依赖缺失提示；通过受控 SSH 服务与串口设备或模拟设备完成实际连接测试。包装命令通过单元测试不等于真实连接或三平台验收已完成。

## M2 · 跨平台桌面终端

- 确定桌面框架和终端渲染组件，接入现有 PTY 能力。
- 实现本地标签、分屏、滚屏、搜索、主题与快捷键。
- 支持中文输入法、Unicode、粘贴和窗口尺寸同步。
- 为每个会话显示执行目标、工作目录和运行状态。
- 发布可重复构建的 macOS、Linux、Windows 开发预览。

**验收：** 三平台分别完成真实 shell 交互、长输出、窗口缩放、会话关闭与进程清理测试；保留平台限制清单。

## M3 · 工作台内的 Agent

- 通过 Codex app-server 适配器呈现会话、流式输出、工具调用、审批与取消。
- 支持用户选择终端输出或文件作为上下文。
- 显示模型、当前工作目录和实际执行位置，避免本地与远程混淆。
- 明确凭据、配置与会话历史的存储位置。
- 处理引擎崩溃、协议不兼容和会话恢复。

**验收：** 用户能在同一工作台中完成“查看终端错误 → 发送选中上下文 → 审批操作 → 检查结果”，且取消和重连不会重复执行操作。

## M4 · 远程与设备工作流

- SSH 连接收藏、配置导入、密钥代理与跳板机。
- 本地、远程和动态端口转发的独立生命周期管理。
- SFTP 文件浏览、传输队列、取消、重试与覆盖确认。
- 串口设备发现、参数配置、收发显示及可选日志。
- 为远程 Agent 选择明确的部署与执行模型，验证其权限边界。

**验收：** 使用受控测试环境覆盖主机密钥变化、认证失败、端口占用、断网、传输取消、串口拔出和远程任务取消；UI 状态与真实连接状态一致。

## M5 · 可持续发行与扩展

- 为三平台建立版本化安装包、校验信息和升级路径。
- 建立终端性能、资源使用、可访问性和会话恢复回归检查。
- 按明确接口接入其他 Agent 引擎。
- 保持上游 Codex 同步策略、依赖更新和贡献流程可执行。

**验收：** 从干净环境可构建和安装，升级及配置迁移经过验证；发行说明列出已验证平台与已知限制。

## 设计约束

终端基础体验和 Agent 集成同为核心。常规 shell、SSH、SFTP 和串口工作流应能在未配置模型账号时使用。模型调用与离线终端能力的依赖要分开，不能把打开普通终端变成必须登录 Agent 服务的操作。

详细模块边界见 [architecture.md](architecture.md)。
